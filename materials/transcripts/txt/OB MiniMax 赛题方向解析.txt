哈喽大家好！我是来自 MiniMax 开发者关系团队的苏嘉怡 Jerry。今天主要是想跟大家介绍 MiniMax 参与设计的赛题：面向软件持续研发的 SDD（Specification-Driven Development，规格驱动开发）工程上下文工具。

其实 AI 现在已经能够帮我们写出不少代码，但是正如刚才上老师讲的，在真实的软件工程里面，其实是在一个长期运行、不断变化的系统里面持续修改。新增一个功能可能会涉及到多个模块，还要兼容过去的行为，理解历史的上下文为什么这样设计，还要遵循团队共同的开发规则。

现在其实已经有了不少的模型，比如我们 MiniMax M3 已经支持百万 Token 的上下文；然后像 Agent Harness，比如我们 MiniMax Code 也有上下文压缩、记忆保存或者按需检索等方案。这些进展其实让 Agent 能够读到更多的资料，也能够持续执行更长的任务。

但是能读到更多的信息，并不自动意味着知道当前应该遵循什么。一个项目里面新旧的需求可能同时存在，设计文档可能落后于代码，有些看起来可以简化的逻辑实际上是要兼容过去的问题。哪些要求仍然有效？这次修改会影响哪里？怎样才算做对？仍然需要明确的工程依据。

这就引出了 SDD，也就是规格驱动的开发。要把实现行为必须遵守的约束和验收的标准明确下来，用它们来指导设计、编码和测试，并随着项目变化持续维护。我们希望选手能够做一个工具，让这些工程依据能够被现成的开发 Agent 找到、理解和持续使用。

具体来说，选手要做一个 SDD 工程上下文工具，关联需求、设计、代码和测试，把当前有效的要求和约束提供给现成的 Agent，并且持续更新。它接收项目的资料和本次的开发任务，帮助 Agent 弄清楚这次要实现什么、哪些已有行为必须保留、涉及到哪些设计和代码，以及需要通过哪些测试。提供这些信息的时候还要说明依据是来自于哪里，遇到过时记录或者相互冲突的要求也要识别出来。

Agent 负责实际修改代码、运行测试。任务完成或者需求变化之后，工具还要根据确认的变更和执行结果，更新相关的规格、决定和进度，让下一次开发能够接着做，也就是刚才说到的 Handoff。

SDD 可以提供明确的工程需求，上下文工具负责维护这些要求和实际工程之间的联系，并且在任务需要的时候给到我们的 Agent。选手可以结合现有的 Harness 的能力，重点解决项目资料之间的关联、要求的有效性以及变更之后的持续更新。MiniMax 希望通过这道赛题，能够探索我们现在模型与 Agent 的编程能力，怎样可靠地用于持续的研发。

数据库部分可以使用我们的 SeekDB，承载工程资料的存储、管理以及混合检索；记忆和上下文管理可以使用 PowerContext。选手需要设计这些能力如何围绕着工程任务相配合。业务工程和开发 Agent 可以按正式规则复用，核心交付是上下文工具及其效果的证据。最终要回答的是：加上选手制作的工具之后，Agent 是否能够准确地理解要求、更少地遗漏约束，并且能够在连续修改中保持一致。

写一个独立函数的时候，输入、输出和对错通常比较容易说清楚；进入大型工程之后，考虑的范围会明显扩大：
1. 首先是系统约束：一个接口可能会被很多模块使用，某张表也可能承载着已有的任务，修改眼前这段代码还要知道哪些地方依赖它；
2. 其次是历史的债务：过去为了赶进度、兼容旧的用户或适配旧的环境留下的实现，看起来不够漂亮，但直接改掉就会破坏仍然在使用的功能。Agent 需要知道当初为什么这么做，哪些限制今天还有效；
3. 团队的规则：比如某类修改必须补哪些测试、怎样评审、什么时候可以发布。这些要求未必都写在当前的文档里面，与其他人的修改也在同时进行。

因此我们要关注的差距是：能够实现眼前功能，还是进一步做到符合整个项目的要求？上下文工具就要帮助 Agent 找到这些容易被漏掉却影响交付结果的依据。

把这些资料都交给 AI 并不代表问题就解决了。更长的上下文确实能容纳更多信息，但项目的资料目前还是需要人来组织。比如收到一份设计说明，只能说明它和任务有关，还要判断它对应哪个版本、有没有被新决定替代掉；一条新的需求取消了旧的限制，并不意味着其他的约束都可以一起丢掉；找到要求之后还要知道看哪些代码、用什么测试检查。Agent 产品已经在使用文件搜索、上下文压缩和持久记忆等方法，我们的赛题希望在此基础上，面向具体的工程进一步研究如何组织需求、设计、代码和测试之间的关系，怎样在项目变化的时候维护这些关系。

SDD 是规格驱动开发，规格可以理解为共同确认的说明（软件应该做什么、哪些条件必须遵守、怎样做才对）。设计解释怎样实现以及为什么这样选择，代码负责实现，测试检查实际行为是否符合要求。真实的项目通常已有代码、数据、用户和发布的流程，一个新的需求进来，开发者先确认当前有效的要求，再判断影响范围，修改代码完成验证。这次开发还会产生新的信息（为什么选择这个方案、哪些文件发生变化、测试结果怎么样、什么问题还没被解决），这些内容应该成为下一轮开发可以使用的依据。

现在看工具放在哪里：
- 左边是项目已有的资料（需求、设计、代码、测试），SeekDB 可以为这些多元资料提供存储、管理、处理和混合检索能力；
- 中间是选手重点实现的上下文模块，依据本次任务选择信息，维护材料之间的关系，判断要求是否适用，把工作依据提供给右边的开发 Agent；
- 下面的 PowerContext 负责支撑起任务记忆和接续（已确认的决定、需要保留的约束、完成进度和下一步的工具）。

交付内容与验证：
1. 说明当前的目标和有效的约束（这次要改什么、哪些行为必须保留）；
2. 给出相关的设计和实现的线索；
3. 提供验证的方法（什么结果才算符合要求，哪些测试需要运行，哪些结果已经确认）；
4. 任务做了一半时说明清楚已完成什么、下一步是什么。

实现时建议先完成一次局部的修改：工具能够取得有效的要求，关联到代码和测试，Agent 能完成修改并通过验收；接着再挑战需求变化、跨模块任务和会话交接。

最后明确交付目标：
做一个可复用的 SDD 工程上下文工具，关联需求、设计、代码和测试，把当前有效的要求与约束提交给现成的 Agent 并持续更新。最终作品应当有可运行的工具和说明、一段完整的开发演示、代码差异、测试和上下文来源等可核对的结果，技术方案要解释自己的设计怎样能够帮助完成任务。
