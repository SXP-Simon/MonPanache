大家好，我是 OceanBase 的研发工程师罗家伟。今天很高兴能向大家介绍一下 Dify。

现在做一个 AI 应用通常已经不只是调用一次大模型了。模型之外还会涉及企业知识、外部工具、业务流程，以及上线之后的监控和维护。Dify 就位于这些能力的中中间，它负责把模型、知识、工具和流程组织起来，让一个想法不只停留在 Demo，而是变成可以交付和持续运行的一个应用。

知识流水线把企业的文档处理成可以检索的内容。插件生态则负责连接模型和外部系统。下面几项是解决应用上线之后的问题，其中可观测性是用于检查运行过程，包括全链路的日志、Tracing 和成本追踪；人工干预则是控制高风险步骤，比如流程中需要人工审批和审核的节点；Skills 则是去复用一些技能，比如 Skills 里可以包括常用的一些提示词和脚本；Trigger 则是用于自动启动一个流程，Trigger 就是一个触发器，它包括定时、事件和 Webhook 驱动流程启动。所以 Dify 现在已经不只是一个聊天机器人的制作工具，更准确地来说，它是一套位于大模型和业务系统之间的应用开发与运行平台。

这是 Dify 现在全球的社区数据，更新于 2026 年 8 月。现在它已经运行在 1.4M+ 以上的运行设备上，并且有 153k 以上的 Star 数量，被 175 个国家和地区使用。有 2000 个团队正在使用 Dify，并且 280 个企业也在使用 Dify 去构建它们的工作流或者 Agent。

在 2023 年到 2024 年，大量的应用框架开始连接模型、知识库和工具；到了 2025 年、2026 年，Agent 已经能完成越来越复杂的任务，新的任务就变成了：这些能力应该如何被组织、控制和长期使用。因此关注点已经从能不能做出 Demo，转向能不能可靠地运行、能不能被团队复用、出了问题能不能正确地定位。生产中也不是把所有的问题都交给 Agent，通常更常见的一个方式是让 Workflow 去控制边界，让模型和 Agent 去处理智能任务，然后在高风险环节加入人工确认。所以说现在 Workflow 依然有它自己独特的一个价值。

接下来是传统开发和现在的 LLM 原生开发的一个对比：
左边的传统软件更强调确定性，条件明确、数据结构明确，测试结果通常也是通过或失败；
右边的 LLM 应用则带有很大的概率性，它的表现会受到 Prompt、上下文、模型版本和检索结果的影响，所以测试不仅要看功能是否运行，还要看准确率、相关性和幻觉率。
两种方式并不是互相替代的，比如做合同审查，条款理解和风险摘要可以交给模型，但是用户权限、金额阈值和最终审批仍然是需要确定性规则的控制。所以可以简单地概括成一句话：模型去处理意思，代码去控制边界。

接下来是 Workflow 工作流编排的一个简单讲解：
第一步是定义输入；第二步是检索知识；第三步是由 LLM 或者 Agent 去完成智能处理；最终再把结果汇总成稳定的格式并进行输出。
正式的流程其实还会加入分支、循环、工具调用、人工审核和异常处理，但其实基本思路并没有改变，它就是把一件复杂的事情拆成职责明确的步骤，也就是工作流 Workflow。比如做多平台内容生成，模型去负责理解和生成，Iteration 去逐个负责平台处理，Template 负责固定格式，If-Else 则负责拦截无效输入，如果输入合理正确才进行下一步节点处理。需要理解的就交给模型，需要控制的交给确定性的节点。

接下来是 Dify 的四种应用形态，不同的形态其实也可以组合，比如 Agent 也可以作为节点进入 Workflow。这四种形态可以按两类问题进行区分：用户是否要进行持续对话？用户步骤能不能提前确定？
其中 Chatbot 适合普通的多轮问答；
Chatflow 适合在对话中加入分支和步骤；
Workflow 则更偏向一次完整的执行；
Agent 则是适合下一步需要根据上一步的结果去动态决定任务，Agent 其实就有更多的思考环节在里面。
关键是它们可以互相组合，比如 Chatflow 就可以去调用一个 Agent，Workflow 也可以将某个复杂的步骤去交给 Agent。所以实际系统往往并不是四选一，而是它们之间有相互的结合。

接下来是 Dify 的核心节点类型，主要是包括四类节点：
第一类是输入输出：输入定义输入格式的 Schema 去触发工作流执行，相当于 Workflow 的起始节点；输出则是 End 节点，定义输出格式并终止工作流。
第二类是处理节点：主要有 Code 节点（可以在 Code 节点里编写 Python 或 Node.js 代码执行，方便进行数据格式转换）和 Template 节点（主要用于字符串模板渲染和提示词构建）。
第三类是 AI 类节点：主要是 LLM（对大语言模型进行包装，支持 OpenAI、千问等多个供应商及参数设置）、Knowledge（知识库检索，即 RAG 上下文注入）、Agent（在受控环境中自主调用 Skills、Bash 和工具完成复杂任务）。
第四类是控制流节点：比如条件分支（用于表达式路由）、Iteration（用于列表迭代批量处理数据）。
通过这样功能明确的分类，不仅能减少 Token，也能让流程更加容易预测和维护。

Dify 在 2026 年介绍了新一代的 Agent。如果接触过 Codex 或者 Claude Code 的同学，这个结构会比较熟悉。模型不只是去回答一次，而是在循环中不断判断下一步做什么。首先它会分析任务，再去使用 Skill、Bash 或者工具去执行动作，观察结果之后再进行持续判断。这个过程其实就是我们熟知的 ReAct loop，可以简单理解为判断、行动、观察，然后再去判断。但生产环境不能只有这个循环：模型怎么切换？上下文太重怎么办？运行环境怎么去回收？失败以后是重试还是停止？这些工程问题被 Dify 概括为 Loop Engineering。
右下角是安全边界，根据 Dify 官方文档，企业版可以按会话去启动独立的 Sandbox，并提供 PID、文件系统和网络隔离。Agent 可以去执行任务，但必须是在受控环境里。

那么问题来了，既然有了 Agent，为什么还需要 Workflow 呢？
其实 Agent 解决的是个体能力，个体能不能去完成任务；Workflow 解决的是这种能力怎么被组织和调度。Agent 非常灵活，它可以根据中间结果去改变行动，但是这种灵活也带来了不确定性。什么时候去启动？可以访问什么？失败之后怎么去处理？结果去交给谁？这些问题往往是需要 Workflow 去提供一个边界。
比如右下角 Calendly 的案例其实很直观：工作流每天定时启动，Agent 读取当天会议，再通过 Gmail 去发送提醒，最后由工作流记录成功或失败。Agent 负责处理任务，Workflow 负责让这件事情每天以受控的方式去发生。

接下来是 Dify 的可观测性与调试：
这一页主要展示了一次执行记录：输入校验用了多久、知识库召回了哪些内容、Agent 执行了几步、调用了几次工具、每次工具的执行结果是怎么样、最后是否成功。
普通的 Workflow 主要是需要去关注节点输入输出；加入 Agent 后还要仔细观察每轮主要调用了什么工具、使用了什么参数、最后返回了什么内容，以及最终为什么会停止。
调试时可以从三个方向去检查：步骤和变量有没有传错、失败之后是应该去重试还是降级、以及工具调用是否符合预期。Run ID 则用于把 Dify 内部记录和外部日志关联起来，我们可以通过 Run ID 精确查找日志。

第三部分是 Dify 的知识库：
主要分为左右两条流水线：左边是 Ingest pipeline（知识入库），右边是 Query pipeline（知识提问后检索）。
知识入库并不是简单地上传文件，文档需要经过解析、清洗、分块、向量化以及索引。如果这个阶段丢失了标题、表格关系或关键上下文，后面的模型再强也找不回来了，所以 Ingest 决定了召回的上限。
右边处理用户问题：系统可以先补全意图或者改写查询，再进行语义和关键词检索，通过 Rerank 进行重新排序，最后把最相关的内容再交给模型处理。比如用户提问“超过 5000 怎么处理”，系统应该结合知识库制度补全问题后找到相应的规则和审批决策，而不是只搜索“超过5000”这几个字。

分块策略：
分块策略就是把长文档切成适合检索的小段，这属于知识入库阶段的流程。但它也不是切得越小越好，切得太小完整信息会被拆散，切得太大又会把无关内容提交给模型。页面中的 800 字符和 80 字符重叠只能作为起点，不是通用答案。普通文档可以从 Recursive 开始，Markdown 适合用于标题分级，代码要尽量保持函数边界，表格则要避免把表头和数据拆开。真正有效的调优方法是准备一组实际的问题，看正确内容能不能稳定召回。

检索策略：
语义检索擅长找意思相近的内容，但遇到产品型号、合同编号或精确条款时只看语义可能不够，因此生产中常常需要使用到混合检索。向量检索负责语义，BM25 负责关键词检索，两边先找出候选内容，然后经过 Rerank 进行重排序，最终只保留最关联的几项片段。召回更多并不一定越好，候选太多会增加时间和成本，太少又有可能漏掉答案。Top K、Top N 和分数阈值都应该用真实的业务问题进行验证。如果存在权限或者时效要求，还应该加入部门、版本和访问权限等元数据过滤。所以 Dify 可以支持向量检索和关键词检索两路召回，再通过 Rerank 重新排序，还可以通过元数据过滤对知识库片段进行更精细的过滤。

部署与集成：
这部分展示了最短的部署路径：首先 git clone Dify 最新源代码，进入 docker 目录复制配置文件，之后 docker compose up -d 一键就可以部署起来。
Dify 也不是单容器应用，除了 api、web 和 worker 容器，还有数据库 Redis、向量存储、Agent backend 和 Sandbox 等服务。页面能打开以后，可以通过 `docker compose logs -f <容器名>` 查看对应容器的具体日志。

Dify 生产架构：
从上到下看：
首先是入口层，主要负责 HTTPS、WAF 和负载均衡；
应用层部署了 API、Web、Worker 和 Agent Backend 容器；
Agent 执行层承载的是 Sandbox、Skills、Bash 和工具调用；
下面是数据层和异步任务层：关系数据库保存应用状态（元数据库），现在 Dify 的元数据库已经支持了 PostgreSQL、MySQL、OceanBase 和 SeekDB 等多种数据库；Redis 承载缓存和队列功能；对象存储保存文件；向量数据库保存知识索引（默认使用 Weaviate，也可以切换为 Milvus、OceanBase 或 SeekDB）。
Agent 执行层需要特别关注安全，除了使用非 root 用户，还要限制容器权限和网络访问。

关键环境变量：
第一组是控制台和应用的访问地址，最常见的问题是 localhost 的用错；
第二组是 DB_TYPE 和 VECTOR_STORE，我们可以通过配置这两个值进行定制化部署。比如把 DB_TYPE 换成 OceanBase 或 SeekDB，把 VECTOR_STORE 也修改成 OceanBase 或 SeekDB，这样我们就可以用一个 OceanBase 或 SeekDB 同时承担元数据库和向量数据库的功能；
第三组是 Redis 和文件存储；最后需要注意的是，生产环境中的密码和密钥不应该直接写在代码仓库里，而是应该通过 Secret 或手工配置注入。

整套内容可以归纳为四句话：
Workflow 负责组织和调度；
Agent 处理路径不确定的复杂任务；
Knowledge 提供可信的上下文（即 RAG）；
Production 保证系统稳定安全地运行（包括监控、诊断和异常处理）。
