那随着就是说我们在各行各业里面，然后包括就是说在日常的这个工作和生活中深度的去使用这个 Agent 以后，其实会遇到很多这个上下文协同的问题。那早期的话其实第一个问题是它的来源是非常分散的。就是我们第一步其实是会需要做的一个重要事情是如果说我今天要做解决一个具体的任务，那我需要从不同的这个背景里面先把这些信息至少去提供给模型。那比如说在一个典型的软件开发的任务里面，那可能会涉及到一些，比如说这个任务它本身是由工单发起的，那它可能是来自于一个具体的客户反馈。然后在这个客户反馈里面它可能会提供一些有效信息。此外呢就是我们其实是需要就是说把代码然后也纳入到这个输入里面，因为我们其实在解决问题的时候作为一个软件的一个厂商，其实我们有很多时候都在以编程的形式来进行工作。那然后在之后呢就是做做了一些修改以后，我们其实是需要检查这些修改是不是有效。那这个时候其实是需要根据日志，然后包括一些可以跟踪的信息来进行处理。那么也就是说，在上下文工程里面有相当一部分的这个工作其实都在这个集成和这个集中的这个治理上面。

那然后另外一个部分呢就是说我们现在使用的大部分的工具其实都是以会话，然后作为一个基本单元的。也就是说我们在每次新建一个就是任务的时候，通常情况下在 Agent 的表现里面是开了一个就是 Session。那这个 Session 其实它是一个天然彼此之间会有一个隔离的一个部分。所以那在一个会话结束以后呢，它所有的这个信息它就只在这个会话里面流转。甚至可能会因为中间的一些压缩，然后以及其他的一些动作，然后可能会丢失。那如果说我们这个时候在一个新开的另外一个任务里面想要获得关于这个会话的上下文，其实就变得非常难了。那这个时候其实是过去就是上下文工程里面着重解决的一个部分，就是怎么样让一个会话的信息能够被其他的这个会话所共享。

这个共享其实是两个方面的：第一个方面就是说在同一个 Agent 里面，就比如说我们今天都用 Codex 或者 Claude Code，然后那在一个 Codex 里面就是我怎么样去引用另外一个会话，或者另外一个会话中已经有的知识。那这个其实在去年的时候其实根本就没有相关的一个就是说由 Agent 内置能力，通常就是说是需要引入一个外部的一个上下文的一个工程的一个组件，比如说一个典型的 Memory 组件。像 OB 之前其实在这一块其实开发了一款叫做 PowerMem 的一个一个软件，就可以用于这个场景。

那刚刚其实讲的就是说这个共享的问题，但是共享其实并不能解决所有问题。比如说我们可能会要把一个内容就变得很长，然后它其实没有办法在一个会话窗口里面完整的表达。那在这种情况下其实是需要就是说对这个内容做截断压缩，然后在召回的时候去做一些精细化处理。因为通常情况下我们做了这个对会话历史的一个提取，然后把它就是变成一些记忆或者经验的时候，它其实是变成一条一条的这种信息。那这些信息其实是只有一部分会对当前的任务有效。那在这个时候就涉及到一步检索的一个情况。在这种情况下我们其实是会给它设置一个最大召回的一个预算，然后包括就是哪些其实是我们能够可信的一个内容，然后我们会把它的权重会调到一个相对比较高的一个水位上面。那对于一些就是权重比较低、长时间没有召回的内容，出于节省存储空间和避免无关信息干扰上下文的考虑，我们可能会对它进行标记删除，或者就是直接从我们的这个存储系统中把它移除出去。那最终呢就是所有的这个就是我们前面做了这个上下文的汇聚，做了会话之间这个上下文或者说记忆的一个共享，然后对召回做了一些精细化的调整以后，我们最终所有的内容都其实还是要服务于它解决的具体问题。比如说对于软件研发来讲，那就是它是不是真正的正确的然后解决了这个工单，或者说它是不是正确的通过了所有的测试、所有的性能指标；那对于这个陪伴类场景的话，就是它是不是真的就是提取到了就是特定的一些记忆。那这些就是说通过一些就是基础设施的能够提供的一些验证指标的一些反馈，包括就是搭建的这个测试测评的系统，那我们其实是可以追踪就是整个上下文的一个效果，然后最终再对这个流程然后去进行调整。所以就是在整个的这个链路上其实上下文工程还是有很多就是有价值的工作是需要去做，然后来帮助就是在一些长程任务中或者是一些这个特定的陪伴类任务中产生具体收益。

那在刚刚讲的过程中其实有相当一部分都落在就是最开始的这个集成上面，我们其实也会看到就是 Agent 对上下文的需求其实是越来越丰富的。这里面不光是我们个人的一些就是日常使用的一些 Agent，就是包括在一些企业内部的一些流程平台，它现在其实也会去做 Agent 化。比如说像我们这次大赛的合作方 Dify，它其实就是去做 Agent 的这种 Workflow，它会涉及到多个编排的工作，那它内部其实也会产生大量的上下文沉积。那包括像这种多 Agent 的 IM 工具，它现在支持就是在群聊里面去添加各种各样的 Agent，然后去协作的去完成任务。那在这种情况下，我们会看到就是不同的场景它对不同的这个上下文它其实提出了各种各样丰富的需求。如果说只是在个人办公场景，那可能对于工程师来讲更重要的就是代码仓库跟这个工单系统，但是对于运营同学可能有相当一部分的这个上下文都集中在，比如说像 PPT，然后比如说像这个视频脚本的一些制作。那然后对于这个整个企业的这个 Workflow 里面，它其实是可能会需要关联到它的知识库，然后以及它的一些工单系统和这个 IM 里面。那对于这个多 Agent 协同的时候，那其实就是所有这些可能涉及到的一些上下文的这个来源都要囊括在内外在内之外，然后它其实还需要就是对这个权限进行一个综合的一个治理。因为比如说我我跟我的 Agent 进行协同，然后你跟你的 Agent 进行协同，然后在一个群聊里面，然后你去尝试去让我的 Agent 去提供一些就是可能比较隐私的数据，那这个其实也是一个就是上下文工程里面需要面临的一个现实问题。因为我们不可能假设所有的这个就是都是处在一个好人群或者说大家都是处在一个非常友善的一个状态下，因为这个在一个就是说更更广阔的一个就是实验场景下是不太不太可靠的。对。
