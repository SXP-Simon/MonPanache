上一位王老师已经向大家讲解了 SeekDB 里面的一些技术细节。我这一部分主要讲 SeekDB 是如何通过 hipVS 的方式让 SeekDB 在 AMD GPU 上获得加速的，以及 hipVS 和 SeekDB 是一个什么关系，以及主要的接入方式。

首先，hipVS 它是等同于 cuVS 的一个存在，它是将 cuVS 带到 AMD ROCm 生态里面的同等产品。对于 cuVS 大家应该不陌生，它是 ANN 算法在 CUDA（也就是英伟达 GPU）上的向量检索库。那 hipVS 是完全在 AMD GPU 生态等同于 cuVS 的。它主要是向上兼容我们的 AMD GPU，向下提供 cuVS 一样的接口。

那 hipVS 里面具体是什么呢？它覆盖了算法、接口还有 ROCm 的运行时。我们可以这样理解：向上，我们的 hipVS 是兼容 cuVS 的这个库的，我们 hipVS 不会自己定义一套新的接口，而是复用 cuVS 的接口。也就是说向上我们提供统一的接口，向下我们让 ANN 算法常用的近邻搜索、精确搜索的算法在 AMD 的 GPU 上调优、加速。这个是 hipVS 的一个主要的内容。

好，那通过之前的介绍我们可以知道，hipVS 向上提供的是一套和 cuVS 一模一样的一套 C 的接口，那就很方便地集成到我们的 SeekDB 里面来，因为 SeekDB 已经支持了 cuVS。我们只需要把接口做对接就可以了。那这张图也很好地展示了一下 hipVS 和 cuVS 的关系：cuVS 是用在英伟达 GPU 的 CUDA 后端上，然后我们的 hipVS 是用在 AMD 的 GPU 上的 ROCm 生态里面。

接下来 SeekDB 是如何接入到 hipVS 的？当然我这里面不会去覆盖非常细节的部分。通过之前的介绍大家已经了解到 hipVS 它其实没有自己定义接口，这就意味着 hipVS 其实可以非常方便地复用 cuVS 的接口以及接入方式。那实际我们也是这样干的。
首先 SeekDB 我们一条 SQL 语句过来之后，会变成这样一个 C API 的一层，下一步就变成 C/C++ 的一个桥接的部分，然后再走到 hipVS。在这里会根据我们是支持 GPU 后端还是 CPU 后端进行分类：如果是 CPU 后端我们走的是 LibVS AG，如果是 GPU 后端我们走的是 cuVS。也就是说在 AMD 的 GPU 上我们通过 hipVS，但是对于 SeekDB 来说它并不知道是 hipVS 或者 cuVS，它只管 cuVS 接口，因为我们的 hipVS 使用的 cuVS 的同一套接口，也就是 hipVS 对 SeekDB 其实是隐身了。但是我们里面的支持链接是这样的一条链，就是一条 SQL 是最后怎么传导到 AMD 的 GPU 上，这是它的一个传导链接。具体的支持只需要一个薄的 C API 的兼容即可。

如果大家对这一部分有兴趣，我们后面也会在 AMD ROCm 的赛道增加更多的材料，包括里面具体的 PR。因为 SeekDB 现在 hipVS 目前处于开发阶段，在大赛正式开始的时候应该已经完成开发。后续会放出更多材料，包括具体支持的细节、PR 以及更多细节，大家如果感兴趣可以参考。

好，那 SeekDB 接入 hipVS 以后在 AMD 的 GPU 上到底运行得怎么样？这个也是大家关心的一个点。

首先我们看看这个速度。单查的话，因为 SeekDB 在 CPU 上的优化已经是毫秒级或者是低于毫秒级（叫亚毫秒级），所以它是非常快的。但是如果只是一次调用几个请求、处理几个请求的话，其实 GPU 它的效果是完全发挥不出来的。在这个图里面也很好地展示了这一点。

看这一张图：如果批次请求一次很少的话，其实 GPU 的耗时/延迟是高于 CPU 的；但是随着批次请求（吞吐量）越来越大，那 GPU 的延迟就降低了。这个是 GPU 的一个加速比（相对于 CPU 而言）。也就是说调用的吞吐量越大，它这个加速比就越来越明显。这也符合 GPU 和 CPU 这两种架构的直觉：CPU 是对于简单的、计算开销小、吞吐量不大的任务比较好；但是 GPU 对于吞吐量大的、批次处理的任务要比较友好。所以在这里也很好地展示了这一特性。
