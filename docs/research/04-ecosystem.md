## 1. 对比总表

| 方向 | 培训核心主题 | 更适合的基础 | 首要外部条件 | 最大不确定性 |

## 2. E1 AMD：先找到 GPU 真正值得加速的部分

**证据。** T13 讨论 hipVS、ROCm 与向量检索接入；当前官网也介绍 GPU 检索方向。hipVS 官方 README 说明其源于 cuVS 移植，并提示多 GPU／多节点仍属实验范围。本次未验证具体设备上的安装兼容性。[hipVS 官方仓库](https://github.com/AMD-Ecosystem/hipVS)

**建议最小方案。** 同一向量集合和距离函数，先跑 CPU 精确结果，再接 GPU 检索并核对返回 ID、距离、Top-K 和批次顺序；最后接入 seekdb 所需接口。先用小数据保证端到端正确，再提高规模。

**优化顺序。** 复用索引／显存 → 合并查询与减少 CPU–GPU 数据往返 → 异步传输和计算重叠 → 调整索引／搜索参数 → 按负载选择 CPU 或 GPU。是否允许动态选择须服从题面。

**评测。** 同时给出构建耗时、查询吞吐、p95、Recall@K、显存峰值和端到端耗时；区分 GPU 计算本身与拷贝、排队、初始化。扫描向量数、维度、批次大小与并发，找出 CPU／GPU 的盈亏边界。

**关键反例。** 单查询、短批次、显存不足、过滤后集合很小、索引重建、插入／删除、并发取消、资源释放失败。不能把 GPU kernel 时间直接当成用户查询耗时。

**选题前确认。** 硬件型号、ROCm／hipVS 版本、远程资源时段、是否允许第三方索引、部署包与测试机是否一致。没有可持续使用的硬件，不建议先把全部备赛时间押在这里。

## 3. E2 阶跃星辰：端侧向量化与检索闭环

**培训预告。** T14 提及浏览器或客户端本地 embedding、seekdb 检索和端侧推理。是否强制使用某开源模型、禁止远程替代等，需要在正式题面复核，不能把转录中的数字当当前模型规格。

**建议最小方案。** 用户输入文本 → 端侧模型生成向量 → 查询 seekdb → 展示带来源结果。文档与查询必须使用兼容模型和归一化方式，记录模型版本、维度和 tokenizer。只要向量空间不一致，接口跑通也没有意义。

**优化。** 模型加载／缓存、Web Worker 避免阻塞界面、批次 embedding、增量处理、量化与兼容降级。若题目允许，可考虑 WebGPU 与 WASM 两条执行路径；比较速度时同时测检索质量，不能把量化损失隐藏起来。

**评测。** 首次可用时间、冷启动下载量、热启动时间、每秒处理文本量、内存峰值、输入响应延迟、Recall／答案证据质量。覆盖不同能力设备、中文长文本和模型加载失败。

**演示建议。** 展示本地推理进度、向量生成与检索证据，明确设备和执行路径。预计算回放不能证明现场端侧推理能力。

## 4. E3 高德：让路线真正满足约束

**培训预告。** T15 从 POI、路线、位置与用户偏好讨论可演化的出行 Agent。正式任务可能限定具体场景，本节方案只是可验证的准备项目。

**建议最小方案。** 用合成用户与城市公开 POI 构造“起终点、时间、交通方式、预算、偏好”任务；把硬约束和软偏好分开。地图工具返回候选，系统检验时空可行性后生成计划，保留每个推荐的事实来源。偏好更新可交给 PowerContext 管理。

**优化。** 先按空间范围与营业约束筛选，再做兴趣排序；对稳定 POI 信息做缓存，对路线和实时信息设置不同刷新策略；将一次完整计划拆成可恢复的工具步骤；只保存有证据的偏好，避免一次拒绝永久影响所有推荐。

**评测。** 硬约束满足率、不可达／闭店建议比例、工具成功率、计划修订次数、API 请求量和任务完成时间。评估“路线看起来合理”不够，要验证时间窗、停留时间与交通耗时。

**反例。** 同名 POI、跨城市歧义、返回坐标系不一致、路线不可达、天气／营业信息过期、用户中途改计划、多个偏好冲突。API 规范和坐标约定以实施时官方文档为准，本报告未给出可直接调用的 API 参数。

## 5. E4 Dify：让工作流可追踪、可恢复

**培训边界。** T16 介绍工作流、Agent、知识库和可观测性，但不足以确认正式题目是数据库适配、插件开发还是业务应用。不要先写一个大应用再猜它是否符合要求。

**建议最小方案。** 一条可重复的知识问答工作流：受控资料导入 → seekdb 检索 → 来源校验 → 生成回答 → 无证据时明确缺失。把模型、检索、外部工具各阶段的输入输出和耗时记录下来。

**优化。** 对独立步骤并行执行；减少重复 embedding／检索；缩小重排候选；将确定性规则前置；对工具失败设置明确分支、重试上限和状态保存。需要跨会话时再引入记忆，不要每个节点都重复放全量上下文。

**评测。** 每条问题的证据质量、完整任务成功率、p95、节点重试次数、token 和费用。不能只看最后一个 LLM 节点是否生成文字。

**交付。** 工作流配置、依赖版本、脱敏环境模板、样例数据、首次运行说明、失败演示和对照报告。如果正式题目要求底层集成，应把适配契约与集成测试作为主交付，而非仅展示工作流截图。

## 6. E5 Qoder：工程过程必须留下验证证据

**培训预告。** T18 用对账工作台演示调研、规划、设计、编码、测试、打包与汇报。对账只是演示案例，尚无证据它就是正式赛题。

**建议最小方案。** 选择能自动验收的小工程任务，提供需求、约束、测试和变更记录；Agent 完成一次实现，再接受一次需求变更。通过失败和修订过程展示工程能力，而不只展示首次生成界面。

**优化。** 建立可执行验收标准；按依赖拆任务；只提供相关代码与约束；把失败测试转为可定位反馈；保存决策和未完成项；用自动化检查限制回归。

**评测。** 隐藏／公开测试通过率、回归数、人工介入次数、有效修改与无关修改比例、总耗时和 token。任务间保持模型与重试预算一致，防止“多跑几次取最好”造成不公平比较。

**反例。** 需求互相冲突、已有测试不足、错误迁移、仅更新截图而未修改真实行为、声称执行但未执行的测试。交付中保留命令、返回结果和版本，不能用生成的“成功报告”替代实际验证。

## 7. E6 魔搭：形成可运行与可复现的开源成果

**培训预告。** T19 提到创空间 Demo、至少一项开源资产和实践文章，具体领域未披露；正式提交要求仍需核实。

**建议最小方案。** 可公开体验的小型领域 Agent，提供一份清晰的数据／模型／代码或工具资产以及可重建步骤。先让用户跑完一个完整任务，再增加复杂度。

**优化。** 依赖与模型缓存、合理的冷启动处理、小模型／大模型路由、检索证据质量、有限资源下的排队与并发。对路由做独立消融，确认节省成本时任务质量没有明显下降。

**评测。** 首次启动成功率、冷启动时长、并发失败率、任务质量、每任务成本、从零复现耗时。开源资产应与作品能力直接关联，不以堆砌仓库数量替代技术贡献。

**文档建议。** 给出任务定义、数据来源／许可、模型版本、架构、运行步骤、评测样例、失败案例和已知限制；公开演示不得带真实密钥。比赛福利与算力额度以实际领取规则为准。

## 8. E7 MiniMax：SDD 与持续工程上下文

**培训预告。** T20 讨论需求、设计、代码与测试关联的上下文工具，关注有效约束、版本冲突和跨会话交接。可把它理解为“支持已有 Coding Agent 持续完成工程任务”，不是另造一个聊天界面。

**建议最小方案。** 给每个需求稳定 ID，关联设计说明、代码位置和测试。执行一次需求修改后，找出受影响的设计、文件和验证项；会话重启时交付当前有效约束与未完成工作。代码证据引用 commit 与文件位置，避免只引用会漂移的行号。

**优化。** 变更驱动的增量索引、依赖与影响分析、过期约束识别、相关片段选择、状态交接、基于测试反馈更新记忆。语义检索负责寻找相关内容，确定性依赖和测试负责约束“是否真的受影响”。

**评测。** 修改任务成功率、旧需求误用率、漏改率、测试回归、交接后重复工作、上下文 token 和总成本。对照无上下文工具、只做普通 RAG、启用需求／版本关联三组。

**反例。** 重命名文件、需求撤销、两个需求冲突、测试未执行、摘要与代码不一致、不同分支上相同文件名。不能将模型声称完成的步骤直接写成已验证事实。

## 9. E8 原力灵机：历史培训技术参考

**状态。** 本地 T17 与官方课程目录仍有这讲，但当前七家生态图未列出原力灵机。尚不能判定正式赛题归属，建议先保留研究，暂不按一个确定生态题投入重资源。

**培训主题。** HandPose 等样本中的姿态、轨迹、标签及原始数据形成可检索证据，用于去重、质量检查、覆盖分析和补采建议。[T17 导读与原文](../../materials/README.md)

**建议最小方案。** 样本 ID 与原始文件绑定，统一 schema／单位／坐标约定，提取可解释特征和向量，检索近重复与异常样本；用小规模人工审核集验证建议。原始数据定位应贯穿处理流程。

**优化。** 增量特征、批次推理、多模态融合、分层去重、覆盖度采样和质量规则。先证明规则对应真实坏样本，避免把少见但有效的动作都排除。

**评测。** 重复检测 precision／recall、异常误报率、覆盖提升、每样本成本、回查原始证据成功率。按采集会话或主体划分数据，避免相邻帧泄漏到训练与测试两侧。

## 10. 生态作品的共同原则

一个小而完整的闭环应包括真实输入、明确约束、可见结果、证据、失败处理和可重复评测。数据库与上下文工程应承担明确作用：存什么、怎么检索、为何更新、如何验证。只把 seekdb 放在依赖列表，不能证明实际技术贡献。

正式题面明确后，先确认强制技术组件和交付格式，再决定上述哪些模块值得实现。尤其不要凭培训预告假设可以使用任意模型、远程服务或现成平台替代要求的核心实现。
