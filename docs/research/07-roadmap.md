# 07 · 选题与推进计划

[返回研究总览](README.md)

## 1. 当前建议

在没有你的完整技术背景、可用时间和正式分值时，先按依赖与可验证性安排：**用一条主线建立可运行基线，再选一个相邻模块做优化。** 不建议同时启动数据库事务、GPU 引擎、长记忆平台和大型生态产品四套工程。

这不是要求报名选一个互斥赛道。正式规则允许的情况下，可以跨类选题；在规则未确认前，也不能保证跨类提交一定可行。

## 2. 按基础选择主线

| 当前优势 | 建议主线 | 可复用到的方向 | 首个完成标志 |
| --- | --- | --- | --- |
| Python、应用开发与 LLM 使用较熟 | PowerContext 检索、预算或交接 | MiniMax、高德、Dify、Qoder 类场景 | 小数据集有明确基线和错误归因 |
| C++、Linux、调试较熟 | seekdb AI Functions 或明确的局部模块 | 后续 File SQL、AI 列、系统优化 | 原始版本构建成功，相关测试可跑 |
| 信息检索／机器学习基础较好 | 向量／全文／混合检索评测 | seekdb、PowerContext、端侧 RAG | 精确真值与质量—延迟曲线 |
| 前端、浏览器、本地推理较熟 | 端侧 RAG 小闭环 | 阶跃星辰、可体验 Demo | 模型冷／热加载与检索正确性可验证 |
| GPU 与并行计算较熟且有设备 | AMD／hipVS 集成与批次优化 | 向量系统性能 | 同质量 CPU／GPU 对照已跑通 |
| 暂时没有明确优势 | 先读规则、运行最小环境、读一个调用链 | 再据反馈选择 | 能解释一次请求从输入到结果的全程 |

表中没有给“保底得分”：分值和隐藏测试未知，任何成功率数字都缺乏依据。

## 3. 三种可控的准备方案

### 方案 A：上下文检索与工程任务

读 T10–T12 和 T20 → 固定 PowerContext 版本 → 构造小型记忆查询集 → 比较原始检索与已有重排 → 针对时间冲突或预算遗漏做一个改进 → 用工程任务验证收益。

优势是可观察的 Python 流程与明确应用闭环；代价是模型结果随机、评测成本和事实标注。先用少量可人工验证样例，再扩大数据。

### 方案 B：AI Functions 与可靠批处理

读 T05、T07 → 跑通 seekdb 原始构建 → 读表达式与客户端 → 建立可控模型服务替身 → 复现批量／错误／超时路径 → 根据实际瓶颈做局部优化。

优势是输入输出明确、容易写稳定回归；代价是 C++ 工程规模、内存生命周期和数据库测试环境。不能一开始就假设已有批处理完全无用。

### 方案 C：检索质量与系统性能

读 T06 → 准备固定向量和查询 → 精确搜索建立真值 → 原始 ANN 曲线 → 加入过滤与写入 → 比较候选、融合和重排。只有已有 AMD 设备和稳定环境时，再接 GPU 支线。

优势是可定量比较；代价是数据规模、正确真值和高维参数空间。每轮只改变少数变量。

这些都是准备方案，拿到题目后必须与实际要求逐条对齐；不符合评分范围的实验应及时停止。

## 4. 题目筛选表

正式题单发布后，对候选题填写以下六项，再排序：

| 维度 | 低风险特征 | 高风险特征 |
| --- | --- | --- |
| 规则清晰度 | 输入输出、验收、分值明确 | 多处描述冲突或缺少关键接口 |
| 环境可用性 | 本地与平台基线已跑通 | 设备／账号／依赖还拿不到 |
| 可测试性 | 有确定性真值或强验收规则 | 只能主观评价演示效果 |
| 依赖复用 | 现有工作直接支撑 | 需要另开一套不相关技术栈 |
| 实现边界 | 局部接口、少量依赖 | 事务／存储／调度全局改动 |
| 交付余量 | 完成后有回归与提测时间 | 最后一天才能首次跑通 |

若已有分值，可用“预期可获得分数／总投入时间”辅助判断，但完成概率必须来自自己的试做证据，并把环境、评测和集成时间计入。不能只用官方标注难度排序。

## 6. 团队分工

**单人：** 环境、实现、评测都要做，优先一条主线，定期留出复现与文档时间。

**两人：** 一人负责核心实现，一人负责评测／应用集成；共同维护边界用例。评测不能等实现完才开始。

**三人：** 核心实现、数据／评测、集成／交付各一人；至少两人能独立重建环境。跨方向选题前，确认成果能复用，而不是三个人各做一个无法集成的大项目。

## 7. 每日工作闭环

每天保存一个可以回答的问题：今天哪项假设得到证据？如果没有改进，失败归因是什么？下一步是改实现、改实验，还是终止该方向？

建议在每个有效提交中关联：题号、修改范围、测试结果、环境／数据版本和仍未通过的边界。原始结果不能只存在聊天记录或个人终端里。

## 8. 明确停止条件

- 无法获取必要硬件且无可接受替代时，暂缓 GPU 支线。
- 两轮实验收益均落在测量噪声内，先改进测量或寻找其他瓶颈。
- 更快但破坏正确性、召回、权限或版本一致性，回退该优化。
- 题面不允许的外部服务／缓存／依赖不继续投入。
- 临近截止仍需改变核心数据格式或事务路径，先保护已验证版本，再评估风险。

停止一个不成立的优化是研究结果；完整记录原因能避免团队再次走同一条路。
