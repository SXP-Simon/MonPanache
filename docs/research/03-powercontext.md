# 03 · PowerContext：上下文质量、记忆与工程优化

[返回研究总览](README.md) · P1–P7 是研究主题，不是官方 11 题题号。

## 1. 它解决什么

Agent 的长任务会不断产生来源、事实、决策和执行结果。把所有历史都塞进提示词，成本高且未必可靠；只做相似度检索，又可能找不到有效约束、时间变化和失败经验。PowerContext 方向研究“收集什么、如何组织、检索什么、给模型多少、更新后以哪一版为准”。课程主要依据 T10–T12。[原文索引](../../materials/README.md)

当前官网把上下文采集、解析、组织、检索、压缩、记忆更新和运行时注入列为方向，关注相关性、任务效果、推理成本和可解释性；11 道正式题的拆分未取得。[官方概述](https://mdn.alipayobjects.com/huamei_22khvb/afts/img/A*WY7oRLa9-iYAAAAAgCAAAAgAeiGDAQ/original)

## 2. 必须区分的概念

| 概念 | 研究时的理解 | 常见混淆 |
| --- | --- | --- |
| Source | 可追溯的输入或证据来源 | 把模型生成的总结当成原始事实 |
| Artifact | 经过组织、生成或修订的制品 | 把各种制品都当成普通字符串 |
| Memory | 可检索和修订的记忆内容 | 把所有聊天逐句永久保存 |
| Experience | 可复用的任务经验 | 把一次偶然成功写成通用规则 |
| Skill | 可复用能力或方法相关制品 | 与事实记忆不加区分地召回 |
| Scope | 数据与操作的作用域边界 | 只在界面过滤，底层已跨域检索 |
| Revision／citation | 指向具体版本的身份与引用 | 只保留“最新版”链接导致证据漂移 |
| Handoff | 为后续会话／执行者保存可继续工作的信息 | 只有摘要，没有未完成事项和验证状态 |
| Context Pack | 按契约选择、渲染并交付上下文 | 随意拼接检索文本、调用方再重复截断 |

上述是阅读辅助；具体类型与接口以固定源码为准。[研究版本 README](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/README_CN.md)

## 3. P1：检索与重排

### 已确认的实现

`MemoryService.search` 负责检索流程并可调用 reranker；`LLMMemoryReranker` 已通过一次结构化生成从候选原始排名中选择结果，过滤重复和越界 rank。若没有任何有效 rank，其代码回退到原始前若干条。**这不等于所有模型异常都静默回退**：RFC 0080 对推理失败规定了可见的失败行为。[服务源码](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/src/powercontext/builtin/artifacts/memory/service.py) · [reranker 源码](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/src/powercontext/builtin/artifacts/memory/reranking.py) · [RFC 0080](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/docs/zh/rfcs/0080_memory_search_reranking.md)

注意：`builtin/scope/search.py` 是作用域发现用的字面子串谓词，并不是 Memory 向量／全文融合主入口。仅凭文件名容易读错路径。

### 建议实验路线

固定语料、embedding、查询和答案模型，依次比较：词法召回 → 向量召回 → 混合召回 → 同候选池加重排。记录候选证据覆盖率、最终证据命中、答案质量、延迟和 token。先判断证据是否进入候选池，再判断重排是否选错；重排无法找回完全没召回的证据。

| 优化 | 适用问题 | 验证方法 |
| --- | --- | --- |
| 查询规范化与精确字段 | 人名、日期、编号、代码符号被语义模糊化 | 同一事实的缩写、中文、英文和精确编号查询 |
| 候选池分配 | 单通道吞掉互补证据 | 按查询类型比较词法／向量配额 |
| 候选多样性与去重 | 多条近似记录挤占预算 | 覆盖不同来源和所需子事实，保留身份 |
| 有条件启用重排 | 简单查询也付出一次模型成本 | 精确匹配与多跳问题分别比较 |
| 重排提示／模型调整 | 模型偏好泛化主题而非具体证据 | 检查 rank、日期、指代与互补事实选择 |
| 结果缓存 | 重复查询频繁 | key 含 scope、数据版本、策略、模型和预算 |

不能把候选文本当执行指令，不能让重排模型创造新的证据身份；要用原始候选索引或稳定 ID 回映射。若需要专用重排模型，先适配已有协议，再验证它的质量和成本，避免另写一条只在 benchmark 生效的“旁路”。

## 4. P2：上下文预算与压缩

### 代码与设计边界

RFC 0028 描述 Context Pack 的选择、引用和总预算，并明确 UTF-8 字节预算；不能把它当成字符数或模型 token 数。该文档包含当前实现修订与未来可能性，阅读时需按具体段落区分，不能把所有构想视为已上线。[Context Pack RFC](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/docs/zh/rfcs/0028_context_pack.md)

**研究建议：** 目标不是把文本缩到最短，而是在预算内保留完成任务所需的事实、约束、引用和不确定性。长文本中最相关一句可能在中间；简单截取前 N 字会制造系统性缺失。

### 可选策略

- 先去除完全重复，再用相关性与互补性选择条目。
- 保留引用与结构，优先抽取证据段落；摘要作为独立派生制品，保留回查来源。
- 为任务目标、硬约束、近期变化和未完成事项设置合理配额，避免某类长内容独占。
- 同时记录字节、token 和运行时预算；若改公共预算语义，应明确兼容性，不能直接把 byte 换成 token。
- 维护省略／截断信息，避免下游以为得到完整上下文。

### 自测

中文和 emoji、极小预算、引用占用预算、单条过长、全部相关条目都放不下、多条重复、只在尾部出现关键限制、恶意指令混入证据。验证输出没有破坏引用或截成非法编码，预算核算包含标签、分隔符和引用。

## 5. P3：记忆写入、去重与时间冲突

### 基线设计

围绕“实体—属性—值—来源—有效时间／记录时间—版本”建立小样例。这里是评测数据模型建议，不要求照搬为 PowerContext schema。

例：3 月用户住 A 城，6 月搬到 B 城。问“现在住哪里”与“4 月住哪里”应取不同证据。新记录不能简单覆盖旧记录，也不能凡是日期新就排前面。

| 优化方向 | 收益 | 失败模式 |
| --- | --- | --- |
| 事件／实体归一化 | 同一事实更容易聚合 | 同名不同人误合并 |
| 重复与近重复检测 | 节省检索和上下文预算 | 删除有不同时间／来源的证据 |
| 冲突检测 | 显式区分旧状态与新状态 | 把互补事实误判冲突 |
| 增量更新 | 避免每轮重处理全部历史 | 更新遗漏、版本指针失效 |
| 重要性／使用频率策略 | 控制容量 | 高频琐事淘汰低频关键约束 |
| 失效／遗忘 | 减少无效召回 | 删除后旧索引或缓存仍可检索 |

建议先做保守、可解释规则，再尝试模型参与的写入决策；所有删除、合并和重写应有证据与可复查历史。生成新记忆时，不能把已有记忆的自我复述无限当作新外部证据。

`source_eligibility.py` 对可用生成来源与绑定制品修订有显式检查，可用来理解系统如何区分普通证据与内部谱系记录。[源码](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/src/powercontext/builtin/source_eligibility.py)

## 6. P4：Scope、权限与证据链

正确性底线：请求只能检索和引用允许的 scope；同样一句话在不同 scope 不等于同一份证据。过滤最好在有权限的候选集合上完成，不能先跨域调用模型再删掉展示结果。

建议对两项目／两用户、相同标题、相同文档 ID、历史版本、删除后缓存、共享来源、权限变更设计测试。检查检索、重排输入、日志、缓存和最终引用是否一致遵守边界。

索引命中只是“候选”；需要确保引用对应的版本仍能验证。若查询期间版本发生变化，应遵循系统已有快照或 head 验证契约，不能偷偷替换成不相同的新文本。

## 7. P5：Handoff 与长任务连续性

建议交接包至少能回答：目标是什么、现在完成到哪里、哪些约束有效、有哪些关键决策及理由、哪些验证真的执行过、下一步做什么、哪些结论还不确定。代码入口是 `builtin/artifacts/handoff/service.py`，已有对应 service 和 generation 测试。[服务](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/src/powercontext/builtin/artifacts/handoff/service.py) · [测试](https://github.com/oceanbase/powercontext/blob/9db1753434162c0aa7c9f1189a1722e617880a52/tests/builtin/artifacts/handoff/test_service.py)

用同一任务做两组：完整单会话与中途强制换会话。对比恢复到首个有效动作的时间、重复工作量、遗漏约束、最终测试通过率和 token。还要提供缺失文件、过期证据和互相冲突的交接说明，观察是否能暴露不确定性。

优化可以是更准确的状态抽取、差量交接、引用有效性检查和失败经验保留。压缩字数不是唯一目标；丢掉“这个测试尚未执行”会让后续模型误以为已经验证。

## 8. P6：Experience／Skill 的积累与复用

把一次成功转为经验时，保留适用前提、执行步骤、验证条件和已知失败。不要把临时路径、一次性账号或偶然环境写成通用规则。建议设置候选、验证、批准等清晰阶段，避免未经验证的经验影响所有后续任务。

实验可构造同类任务的三种分布：与历史相近、局部变化、明显不适用。既测复用成功率，也测错误复用率。复用策略应能选择“不适用”，而不是强行给每个任务找一个 Skill。

这是根据课程与项目制品设计提出的研究方向；尚未证明正式 11 题里有单独的 Experience 或 Skill 题。

## 9. P7：异步执行、可靠性与成本

优先定位：入库／抽取耗时、模型等待、数据库读取、重排、上下文渲染和工具调用。高并发时避免持有数据库锁等待模型，使用有界任务队列与可恢复任务状态；改动必须遵循现有并发和失败语义。

一个有用的成本口径是：`完成一个有效任务的总成本 = 入库 + 记忆更新 + 检索 + 重排 + 回答 + 重试`。不能只比较最后一次回答 token；更不能把昂贵的提前处理藏到统计外。

## 11. 推荐第一项实验

用一个小型、人工可检查的数据集，覆盖精确事实、时间变化、多证据、无答案、跨 scope 和提示注入六类查询。先比较原始 hybrid 与现有 rerank，再按失败归因只改一个环节。能够解释“证据在哪一步丢失”，比一次性加很多模型组件更有价值。
