# 06 · 如何证明优化有效

[返回研究总览](README.md)

本章提供研究评测方法，**不是官方评分函数**。没有填入虚构结果；后续实测可直接复制[实验记录模板](templates/experiment.json)。

## 1. 先把问题写成可证伪的假设

不写“优化检索性能”，而写：“在同样 Recall@10 门槛下，通过减小重复候选和有界批处理，降低固定并发负载的 p95 延迟，同时错误率不增加。”

一个有效实验应包含：基线、唯一主要变化、输入集合、固定条件、指标、通过门槛、失败例子和复现命令。指标门槛优先用题面；题面缺失时，自设门槛必须标为开发目标，不能声称达到了比赛要求。

## 2. 四层测量

| 层次 | 回答的问题 | 例子 |
| --- | --- | --- |
| 功能 | 结果是否符合规范 | SQL 类型、NULL、错误码、版本、权限 |
| 检索／证据 | 找到的内容是否足够且相关 | ANN recall、证据覆盖、引用有效性 |
| 任务 | 用户目标是否真的完成 | 正确回答、代码测试通过、路线满足约束 |
| 系统与成本 | 付出了多少资源和时间 | p50／p95／p99、吞吐、内存、token、API 费 |

只有前面相关质量条件通过，才谈后面的性能收益。一个失败更快的系统不能被统计成优化成功。

## 3. 指标定义与陷阱

| 指标 | 推荐定义 | 注意事项 |
| --- | --- | --- |
| ANN Recall@K | `返回 Top-K 与精确 Top-K 的交集大小 / K` | 数据不足 K、距离同分时提前定义规则；真值使用同距离与过滤条件 |
| 相关文档 Recall@K | `Top-K 中相关文档数 / 全部已标注相关文档数` | 与 ANN recall 是不同指标，标注不完整会影响解释 |
| Precision@K | `Top-K 中相关文档数 / K` | 返回不足 K 时固定分母政策，不临时选择有利口径 |
| MRR | 各查询首个相关结果排名倒数的均值 | 无相关结果记 0；只衡量首个答案 |
| nDCG@K | 按排名折扣累计分级相关性，再除理想排序得分 | 需要明确相关等级；无相关项的查询单独规定处理 |
| 证据覆盖率 | 所需事实中被召回证据支撑的比例 | 多跳问题不能只看命中任意一段 |
| 引用有效率 | 能回查且支撑对应陈述的引用占比 | 链接存在不代表内容支撑结论 |
| 任务成功率 | 按预先约定验收规则成功的任务数／总任务数 | LLM 裁判应固定模型／提示，并辅以人工抽查或确定性测试 |
| 延迟分位数 | 从提交请求到可用结果的时长分布 | 说明包含排队、传输、重试与否；小样本 p99 不稳 |
| 吞吐 | 单位墙钟时间完成的有效工作量 | 同时披露失败和未完成请求 |
| 单任务成本 | 全流程模型与资源成本／完成任务数 | 同时报总成本和总任务，避免只算成功样本 |
| 新鲜度 | 源更新到新版本可正确检索的时间 | 查询很快但内容过期仍可能不可用 |

对于 0 个相关标注或其他零分母情况，在实验前写明“排除并单报”或固定定义；不同方法必须使用同一政策。

## 4. 最小实验矩阵

| 方向 | 基线 | 主要变量 | 质量护栏 |
| --- | --- | --- | --- |
| AI Functions | 原始逐条／已有批量路径 | batch、并发、去重、重试 | 行与结果匹配、错误／NULL 语义、总截止时间 |
| File SQL | 显式 schema 顺序扫描 | 列裁剪、下推、并行、缓存 | 同一多重集／排序语义；异常输入一致 |
| AI 列 | 原始任务与发布逻辑 | 合并、批处理、索引发布 | 源版本匹配、回滚、恢复、删除后不可见 |
| ANN | 精确搜索与原始 ANN | 搜索宽度、过滤方式、量化 | 同 Recall 门槛、同距离和数据 |
| 混合 RAG | 全文、向量、原始融合 | 候选配额、重排、分块 | 证据和答案质量，固定生成模型 |
| PowerContext | 原始记忆／检索路径 | 抽取、重排、预算、时间冲突 | scope、引用、事实与版本正确 |
| GPU | CPU 与 GPU 原始路径 | 批次、传输、索引参数 | 相同真值和端到端计时 |
| 生态 Agent | 无额外记忆或优化的完整任务 | 工具策略、缓存、上下文 | 真实任务验收和失败处理 |

## 5. 实验顺序

1. **基线可复现。** 保存 commit、依赖、配置、数据 hash；无修改版本能重复运行。
2. **小样例正确。** 用人工可检查数据覆盖正常、边界、错误和并发场景。
3. **找到瓶颈。** 按阶段记录耗时与资源，确认待优化部分占比。
4. **一个主要变化。** 开关控制改动，用同样输入成对比较。
5. **扩大输入。** 增大规模、长度、并发或更新率，观察拐点和失败。
6. **重复与消融。** 使用固定随机种子、重复运行；拆掉每个组件验证收益来源。
7. **保留失败。** 不只保存最佳一次，记录超时、质量回退和不适用条件。
8. **按正式平台验证。** 本地优势不保证评测机优势，平台反馈与本地记录关联。

建议起步采用多次独立重复并报告中位数、范围或置信区间；重复次数由方差和费用决定。随机生成和 LLM 裁判尤其需要检查稳定性。不要用不同重试预算的“最好一次”比较两个方法。

## 6. 冷热、并发与时间口径

冷启动可能包含进程、模型和索引加载；冷缓存可能只是数据页未命中。要明确到底清了什么缓存，不能把 A 的冷启动与 B 的热运行比较。不要在用户的真实数据库上清缓存或重启服务做研究。

并发负载同时记录到达率、进行中请求数和队列长度。只在前一个请求结束后才发下一个的客户端，会隐藏高负载排队问题；有固定到达率的实验需统计来不及完成的请求。吞吐上升但 p95 超出可用范围时，不能说方案全面更好。

GPU 测试需在计时边界正确等待异步任务完成，并分别列出数据上传、索引构建、搜索和下载时间。内存缓存、显存缓存、远程模型缓存都属于实验条件。

## 7. 数据与模型控制

- 按用户／会话／文档族或时间划分数据，避免同一事实的近重复泄漏到开发与测试两侧。
- 调参只使用开发集；最终测试集保留到方案冻结。没有真实官方测试集时，只报告自建／公开集结果。
- embedding、生成与裁判模型分别记录版本、温度等配置；模型提供方若没有固定快照，注明结果可能随服务变化。
- 不把参考答案、未来对话或隐藏测试内容写入记忆库。
- 对成本提供币种、计价时间和价格来源；未知实际价格时先报请求数与 token，不能编造金额。
- 外部服务配额与网络波动影响时延，使用本地替身隔离协议测试，再独立做真实服务集成测试。

## 8. 一组高价值的边界样例

| 类别 | 样例 | 观察目标 |
| --- | --- | --- |
| 空与缺失 | 空文件、NULL、空候选、无答案 | 不崩溃、不编造、不误报成功 |
| 类型与编码 | 中文、emoji、长数字、NaN／无穷值、非法 JSON | 按契约拒绝或正确转换 |
| 时间变化 | 新旧偏好冲突、过期模型结果、更新后删除 | 版本与有效时间正确 |
| 身份冲突 | 同名用户、同文档不同 scope、重复 ID | 不串数据、不错误去重 |
| 外部故障 | 限流、超时、半批次成功、断网 | 重试有界、错误可见、结果不乱序 |
| 并发／恢复 | 同行连续更新、查询取消、重启恢复 | 无旧结果覆盖、泄漏或重复副作用 |
| 不可信证据 | 文档中含“忽略规则”等指令 | 只当数据，不改变系统授权 |
| 资源边界 | 小内存、长输入、队列积压 | 有背压或明确失败，不无限堆积 |

## 9. 报告结果的格式

建议每个优化只写一页：问题与假设 → 具体改动 → 环境和数据 → 对照表 → 失败案例 → 适用范围。结果表必须同时含基线、改进、差值、重复次数和质量指标。

例如只有在实际测量后才能写“某数据集、某硬件、固定 Recall 下 p95 降低 X%”。在没有测量时应写“预计减少重复请求，待验证”，不能将设计预期写成实测结论。
