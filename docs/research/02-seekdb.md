# 02 · seekdb：功能补全、检索与系统优化

[返回研究总览](README.md) · 本章主题编号 S1–S5 是研究分类，不是官方题号。

## 1. 理解问题的层次

seekdb 方向的官网概述覆盖存储、处理、检索和智能应用，强调功能正确性、检索效果、系统性能和工程质量。具体 12 题如何拆分尚未核实。[官方说明](https://mdn.alipayobjects.com/huamei_22khvb/afts/img/A*WY7oRLa9-iYAAAAAgCAAAAgAeiGDAQ/original)

培训 T05–T09 提供五个切入点：数据库基础、向量与 RAG、AI Functions、File SQL、模型驱动的 AI 列。以下分析将这些课程主题转成可验证的研究路线。[课程原文索引](../../materials/README.md)

```text
SQL → 解析与语义检查 → 计划生成 → 算子执行 → 存储/索引
                            │
                            ├─ 模型请求 → 协议解析 → SQL 类型结果
                            └─ 文件扫描 → 类型转换 → 过滤/JOIN/聚合
数据更新 → 派生任务 → 模型执行 → 版本检查 → 派生列与索引发布
```

图中下方两条是理解课程的概念链路，不能据此断言当前源码已实现所有环节。

## 2. S1：AI Functions

### 要解决的问题

把模型调用放入 SQL 后，数据库需要管理参数类型、模型配置、协议、资源生命周期、超时和失败语义。难点是大量行输入、模型不稳定和 SQL 一致性同时出现，而不只是发出一次 HTTP 请求。

**代码确认：** 研究版本已包含 `ObExprAIEmbed::eval_ai_embed`、`ObExprAIComplete::eval_ai_complete`、`ObExprAIRerank::eval_ai_rerank`；客户端存在同步、批量和非阻塞批量接口，工具层也有向量批处理路径。不能把“从零添加批处理”直接当作现有空缺。[表达式目录](https://github.com/oceanbase/seekdb/tree/76f871eb5a84b664d487b03b3412ce50194135b5/src/sql/engine/expr/ob_expr_ai)

课程口述可能出现 AI_EMBEDDING 等名称；研究源码入口是 `AI_EMBED` 对应的 `ObExprAIEmbed`。实际 SQL 语法应以指定版本注册和测试为准。

### 最小基线

先建立可控制响应的本地模型服务替身：固定成功、延迟、429、5xx、格式错误、维度错误及断开连接。真实模型用于集成测试和质量验证，协议单测不应依赖真实生成的随机文字。

基线链路：输入参数检查 → 构造请求 → 调用服务 → 校验响应 → 按原行位置返回结果。记录请求数量、每阶段耗时、成功与错误数量。再确认 NULL、空字符串、非法 JSON 和不同 provider 的行为。

### 优化候选与成立条件

| 方向 | 为什么可能有效 | 必须守住的条件 | 首轮实验 |
| --- | --- | --- | --- |
| provider 原生多输入批处理 | 减少请求和重复协议开销 | 单次请求上限、输入与输出索引一一对应 | 同样输入下比较逐条、并发多请求、原生批次 |
| 有界并发与背压 | 等待网络时处理其他请求 | 不超过模型配额、内存与查询截止时间 | 扫并发数，观察 p95、429、排队长度 |
| 连接复用与减少序列化 | 减少重复建连和拷贝 | 客户端／allocator 生命周期与线程安全 | 先用 profile 证明开销占比 |
| 相同输入去重 | 避免重复 embedding | 包含模型版本、配置、文本和权限作用域；失效可解释 | 重复率 0%、50%、90% 的自建负载 |
| 失败分级重试 | 避免瞬态失败拖垮任务 | 仅重试允许的错误；总截止时间、次数和计费上限 | 注入超时与限流，观察重试放大 |
| 请求与结果内存复用 | 降低大批次峰值 | 不能在结果仍引用时释放或覆盖内存 | 大文本、混合长短输入、取消查询 |

这些比例仅为建议实验点，不是官方输入分布。生成函数可能非确定，去重或缓存会改变可观察行为；先明确函数契约，不能只因参数相同就省略调用。对外调用即使 SQL 最后回滚，也可能已经消耗额度。

### 已发现、值得进一步核查的位置

- `ob_ai_func_client.cpp` 有基于查询剩余时间的超时计算，以及单次与批量重试分支。可研究“总截止时间、剩余预算、部分失败”是否在各路径一致；本次没有执行故障测试，**不宣称发现确定缺陷**。[客户端源码](https://github.com/oceanbase/seekdb/blob/76f871eb5a84b664d487b03b3412ce50194135b5/src/sql/engine/expr/ob_expr_ai/ob_ai_func_client.cpp)
- `ob_expr_ai_rerank.cpp` 在读取的路径中使用 20 条批次，并做索引偏移与结果合并。可核查跨批分数可比性、同分稳定性、重复文档和返回索引边界；是否能改批大小取决于 provider 契约。[rerank 源码](https://github.com/oceanbase/seekdb/blob/76f871eb5a84b664d487b03b3412ce50194135b5/src/sql/engine/expr/ob_expr_ai/ob_expr_ai_rerank.cpp)
- 三个表达式的 `cg_expr` 附近都有 AI 函数 plan cache 与 schema version 匹配的 TODO。它是阅读线索，不是官方承诺的赛题，也不是已证明可利用的问题。可构造模型配置变更前后的同 SQL 回归实验。

### 核心自测

参数个数／类型、NULL 与空输入、长 Unicode、JSON 转义、向量维度／数值合法性、批次乱序与缺项、重复索引、部分错误、取消／超时、连续执行内存增长、修改模型配置后的结果、权限隔离。错误应有可区分原因，不把服务错误伪装成正常空结果。

## 3. S2：File SQL for AI Agent

### 培训主题与源码边界

T08 讨论直接用 SQL 查文件、schema 推断、CSV／JSON／Parquet 与关系查询。**本次仅按目录和文件名检索，没有定位到可确认完整 File SQL 实现的入口。** 这不证明功能不存在；可能使用其他命名、尚未合入或需要指定题目基线。不要在未读题前自行设计一个与评分接口不兼容的新语法。

### 最小闭环

受控目录中的单个小文件 → 明确 schema → 顺序扫描 → 类型转换 → 输出关系行 → 与普通表 JOIN。先固定格式和错误政策，再增加自动推断、多文件和性能特性。

| 环节 | 正确性重点 | 可探索的优化 |
| --- | --- | --- |
| 路径解析 | 相对路径基准、规范化、允许目录、符号链接、远程 URI 规则 | 缓存经过权限检查的元数据，文件变化后失效 |
| schema | 空文件、全 NULL 列、同列混合类型、数值溢出、字段缺失 | 显式 schema 跳过重复推断；采样推断需回退 |
| CSV | 引号、转义、嵌入换行、BOM、编码、尾部空列 | 块读取、减少字符串复制；并行边界不能简单按换行切 |
| JSON | JSON Lines 与数组文件区别、嵌套字段、缺失和 null | 只解析需要字段；避免整文件驻留 |
| Parquet | 类型、NULL、压缩、元数据、列与行组结构 | 列裁剪、行组／页跳过、延迟物化 |
| SQL 执行 | 三值逻辑、排序、LIMIT、JOIN 重复行、聚合 | 合法谓词下推、向量批处理、受控并行 |

Parquet 官方格式将数据组织为行组和列块，页索引可提供跳过依据；因此“只读需要列、跳过不可能匹配的组／页”是合理研究路径，但读取器必须实际支持相关元数据。[格式概念](https://parquet.apache.org/docs/concepts/) · [页索引](https://parquet.apache.org/docs/file-format/pageindex/)

### 容易做错的地方

- 抽样推断首批全是整数，后续出现小数或字符串，不能静默截断。
- `x != 3` 对 NULL 的行为不能按普通布尔补集处理；字符串排序规则也会影响下推。
- `LIMIT 10` 能否提前停止，取决于是否还有全局排序、聚合、去重或 JOIN。
- 文件在查询过程中变更时，需要明确快照或错误语义；缓存 schema 不等于缓存稳定数据。
- 并行 CSV 分片必须识别引号状态，不能把字段中的换行当记录边界。

### 实验

固定文件内容，先用显式 schema 的顺序扫描作为真值。比较全列／少列、无过滤／强过滤、短行／长行、冷缓存／热缓存、单文件／多文件。记录实际读取字节、CPU、峰值内存、打开文件数及结果一致性。对于 Parquet，增加“统计信息不足”和“边界值恰好相等”的反例。

## 4. S3：AI 列与派生数据维护

### 核心问题

T09 讨论源数据变化后自动生成 embedding、标签或摘要。外部模型慢、结果可能乱序；事务回滚、重试、进程崩溃和索引更新会让“最终写回一列”变成一致性问题。本节是根据培训形成的设计研究，尚未确认正式题面采用的状态与 SQL 接口。

建议先画状态机：`待处理 → 执行中 → 成功／失败／被新版取代`。任务至少能关联行身份、源版本、派生定义版本和模型版本。行 v1 开始生成后更新到 v2，即使 v1 更晚返回，也不能覆盖 v2。

```text
源行 v1 ──任务 A（慢）──────返回：发现源版本已变，拒绝发布
    └→ v2 ──任务 B（快）──返回：版本匹配，发布结果
```

### 先验证语义，再降低成本

| 问题 | 建议验证的策略 | 不能省略的反例 |
| --- | --- | --- |
| 旧结果覆盖新数据 | 发布时检查源行／定义版本 | 删除后重建同主键、快速连续更新 |
| 重复执行 | 幂等任务身份，重复发布无额外副作用 | 崩溃发生在模型返回后、提交前 |
| 事务回滚 | 按正式可见性规则生成或丢弃任务 | 未提交源值已被模型看到或写入索引 |
| 多个派生字段一致 | 需要时按同一版本整体发布 | 一列成功、一列失败、重启后重试 |
| 索引新鲜度 | 定义派生值与可检索状态的关系 | 更新／删除后仍命中旧向量 |
| 模型／定义变化 | 明确重算范围、版本和渐进迁移 | 新旧维度或语义混用 |
| 积压 | 有界队列、退避、限流、可观测状态 | 服务长期不可用、恢复后突发流量 |

可能的优化顺序：只重算真正受影响的列 → 合并尚未执行的多次更新 → 对有效任务分批 → 缓存确定性结果 → 调整并发与索引发布粒度。合并只能在保留正式可见性和历史要求的前提下进行。

### 指标

成功任务吞吐、更新到可检索的 p95 延迟、队列长度、每次有效更新的模型调用数、重复任务率、过期结果拒绝数、失败恢复时间。单看查询 QPS 会漏掉派生数据越来越陈旧的问题。

## 5. S4：向量、全文与混合检索

### 先拆开三个质量问题

1. **向量索引有没有找准近邻？** 用同向量、同距离的精确 Top-K 作对照。
2. **近邻是不是用户要的证据？** 用人工或数据集标注的相关文档评估。
3. **最终回答是否正确？** 在相同生成模型和上下文预算下评估。

ANN Recall 很高不代表语义相关性高，更不代表最终回答正确。T06 的 RAG 与混合检索是这些层次的组合。[T06 原文入口](../../materials/README.md)

| 优化层 | 可调因素 | 收益与代价 | 最小实验 |
| --- | --- | --- | --- |
| 文档处理 | chunk 边界、重叠、标题与元数据 | 信息完整性对抗重复与存储膨胀 | 固定模型，比较两种分块 |
| embedding | 模型、维度、归一化 | 语义质量对抗算力与索引体积 | 同语料同查询独立建立索引 |
| HNSW 类索引 | 图连接规模、构建／搜索候选宽度 | 召回、构建时间、内存、延迟互相制约 | 扫搜索宽度并画 Recall–p95 曲线 |
| IVF 类索引 | 聚类规模、探测范围、量化 | 更少扫描对抗量化误差与漏召回 | 固定训练数据，验证分布变化 |
| 过滤 | 过滤前置／后置／混合 | 小集合可精确算；后过滤可能不足 K | 覆盖不同过滤后剩余比例 |
| 混合融合 | 全文与向量候选数量、RRF／其他融合 | 精确术语与语义表达互补 | 全文、向量、融合三个对照 |
| 重排 | 候选数、模型、触发条件 | 提升证据选择但增加时延／成本 | 同候选池比较开关与不同 K |

参数名称依赖具体版本和索引库；表中是算法概念，不是保证可直接执行的配置。seekdb 文档中的混合检索示例具有独立候选通道与 RRF，但引用的文档版本为 V1.0.0，不能视为比赛版本的完整 API。[官方版本化示例](https://github.com/oceanbase/seekdb-doc/blob/V1.0.0/en-US/200.develop/600.search/500.hybrid-search.md)

RRF 的基本思想是按排名倒数融合，而不是把量纲不同的向量分数和全文分数直接相加。可写作 `score(d) = Σ 1 / (c + rank_i(d))`，只对出现该文档的通道求和；`c` 为融合参数，不是召回 K。[RRF 原论文](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)

### 常见错误

- 相似度越高越好与距离越低越好混用；cosine、内积、L2 的归一化条件不同。
- 后过滤丢掉大部分候选后仍宣称得到过滤集合的 Top-K。
- 混合召回后只按文本去重，误合并不同权限或版本的证据。
- 只在静态索引测试，忽略持续写入、删除与重建。
- 在小数据上宣称 GPU 必然更快，忽略传输、初始化与批次等待。

## 6. S5：系统性能与稳定性

从 profile 和执行计划找瓶颈，再决定是算法、I/O、内存分配、锁、网络还是模型延迟。先拆分总耗时，再局部优化。若模型耗时占 95%，把剩余 5% 全部消除也只能获得约 1.053 倍端到端加速；这是 Amdahl 思路下的理想上限示例，不是实测。

建议先做局部、可关闭、可回滚的改动：减少无效重复计算、缩短锁范围、有界批次、避免不必要物化、合理复用缓冲区。高风险改动如换 ANN 引擎、改变事务路径、全局调度重写，应在确认题目价值和测试能力后投入。

每个性能结果同时给出正确性、资源峰值和失败率。超时请求不能从统计中直接删掉，降低召回阈值也不能当作无条件性能提升。

## 7. 建议起步顺序

| 你的基础 | 第一阶段 | 第二阶段 | 暂缓 |
| --- | --- | --- | --- |
| C++ 较弱、数据库初学 | 顺着一个 AI 函数读到客户端，补类型／NULL 测试 | 小范围协议或结果处理改动 | 事务／索引全局重写 |
| C++ 与系统基础较好 | 运行正式基线与相关测试，建立 profile | 批处理、内存、执行与索引局部优化 | 没有对照的调参 |
| 检索／机器学习基础较好 | 精确检索真值与固定查询集 | 混合召回、重排、过滤与质量评测 | 先换大模型再解释收益 |

具体题目分值和缺失功能尚未知；以上按学习依赖和可验证性排序，不是预估得分榜。
